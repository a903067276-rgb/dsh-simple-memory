# 记忆系统 v2 设计计划

> 状态：**设计迭代中（用户边补零碎想法边定稿）**，落地前再最终确认。
> 一句话：**信任模型判断（喂概念），不搞机械约束；治理靠池子流动（升格/删减/合并），防膨胀防发散。**

---

## 一、外部调研：可借鉴的成熟机制

2026-08-24 二次调研，补充第一场讨论（官方没做、社区刚起步）之后的增量。四个值得抄的"简单办法"：

| 借鉴自 | 机制（大白话） | 我们怎么抄（最简版） |
|---|---|---|
| **Mem0** | 写新记忆时，让 LLM 判断它和旧记忆的关系，决定 **ADD 新增 / UPDATE 更新 / DELETE 删除 / no-op 忽略** | 把"写前先看有没有同主题该更新/合并"写进记忆判断概念里，模型自判，不做代码级查重（只留一个"完全同名"的保底提示） |
| **Generative Agents（斯坦福）** | 召回记忆按三要素打分：**relevance（相关）+ recency（最近）+ importance（重要）**，取高的注入 | 把"最近踩过、和当前任务沾边、可能改变做法"三个词塞进"忆"的判断概念，模型自权衡 |
| **记忆压缩（Compaction）** | 跨任务边界时，把一堆原始过程**提炼成一条可复用结论**（去噪、合并、抽象） | 这就是"升格 + 合并"的学术原型：项目经验 → 抽象 → 全局通用，同主题散条 → 合成一条 |
| **MemGPT / Letta** | 核心记忆常驻上下文，归档记忆按需召回，压力大了就驱逐 | 我们已有"活跃区/冷区"骨架，v2 把它补成"活跃 → archive 的流动规则"（触顶治理） |

**共识判断**：以上四个都不是重工程（没让上向量库/数据库），本质都是"给模型一个清晰的判断标准 + 一个自然的触发点"。这正好印证用户的方向——**喂概念比机械约束好**。

## 二、现状诊断（v1 为什么只做了一半）

- **记**：能写进去，但①靠灯泡塞模板→机械跑 6 步，重且啰嗦 ②不查重不合并（已发生过标题写重要手动"顺修"）③每次打断确认 + 弹审批。
- **忆**：唯一机制是开头塞 66 个文件名，模型"觉得相关"才读——无召回触发，全靠自觉，且不可验证。
- **整理**：升格暂存池（staging）7 天 **0 次真实运转**（git 历史只建库当天测过一次）；删减/合并/遗忘全是纸面。
- **根因**：v1 缺的不是"约束"，是**概念喂得太含糊**（"相关时按需读"等于没说）；且"记"和"整理"是两段脱节的流程，没人推动后者。

---

## 三、设计原则（简单为纲）

1. **信任模型判断**：不写"命中主题必须先读"这类机械命令，改成喂清晰判断概念，模型自判。
2. **一切落文本**：能改提示词/约定解决的，不写代码；代码只做格式栅栏和保底。
3. **不动存储架构**：继续零代码 md 分层，不建库、不上向量、不引入新依赖。
4. **一个自然触发点**：注入文本 + 灯泡指令，就是全部机制的入口，不新增后台任务。

## 四、核心机制设计

### 4.1 记忆（存储）——基本不动
- md 分层不变：`projects/<项目>/`、`common/`、`archive/`、`references/`、`staging.md`。
- 单条 ≤2KB，首行 `## 日期 分类-主题`，**结论前置**（文件名后面那句就是"管什么事"）。
- 不加摘要/关键词元数据——文件名（分类-主题）就是索引词，够用。有人建议注入时把文件名换成一句话摘要，**不采纳**：那等于给每条记忆加维护负担，违背简单原则，主题词已一眼可判。

### 4.2 索引（清单形态）——只做排序 + 上限
- 保持"文件名按分类分组"的形式（已够好）。
- 排序：当前项目记忆排最前 → 全局其次。
- 上限：活跃区"满即驱逐"——每区设硬上限（项目单区 ~25 条、common ~30 条），超了就按"最久没动"归档到 archive，索引只列活跃区（借 MemGPT 的 memory pressure，简单化）。

### 4.3 注入（喂概念）——改动最大处
把注入文本从"建议"改成"喂三个清晰的判断概念"，**判断权交给模型**：

> 【记忆索引】下面是你过去踩过的坑、做过的决定（不是普通资料）。动手前花一秒扫一眼：**凡是最近踩过、和现在要做的事沾边、可能改变你做法**的，先读再动手；无关的跳过。读完自然用在回答里，不必单独汇报。
> （清单：项目优先 → 全局）
> 收尾时顺手想一句：这次有没有值得记的、有没有该合并/该归档的旧记忆？有就列候选等用户点头。

### 4.4 记（去重/更新/合并）——借 Mem0
- 判断概念（写进 memory-write 描述 + 灯泡指令）：**写前先扫目录——这条和已有的是不是同一件事？同一件就更新/合并旧的，别另起炉灶；全新的才新建；已被替代的就移 archive。**
- 代码保底：memory-write 写入前查"分类-主题.md"完全同名，存在则提示"已有一条同名，是覆盖还是换主题"（十几行）。

### 4.5 忆（召回）——借 Generative Agents 三要素
- 机制就是 4.3 的判断概念：**relevance + recency + importance** 大白话化为"最近踩过 + 沾边 + 可能改变做法"。
- 不做实时 hook 分析对话、不做 embedding——模型读到清晰概念后自己判断。

### 4.6 池子治理（升格/删减/合并/遗忘）——借 Compaction + MemGPT
```
projects/<项目>/  ──升格──>  staging.md  ──确认──>  common/（全局）
       │
       └──删减(过时/被替代)──>  archive/（软删除，可翻）

同主题散落多条 ──合并──> 一条（跨项目则进 common）
```
- **升格判断**："这条换个项目也会遇到吗？" → 会 → 进 staging → 用户点头 → 抽象去项目细节 → common。
- **删减判断**："这条还成立吗？被新结论替代了吗？" → 不成立 → archive。
- **合并判断**："这几条说的是不是同一件事？" → 是 → 合成一条；**同主题攒到 2~3 条就合成 1 条更精炼的总结，原文归档**（借 reflection 的"观察→见解"）。
- **触发点**：写记忆时顺手判断 + 注入文本收尾轻提醒（是提醒不是命令）。
- **UI 治理视图（第二波）**：设置页按主题聚类 + 修改时间排序，同主题多条/久未更新（>30 天）黄字提示，一键归档。

## 六、明确不做（守住简单）

- ❌ 实时 hook 逐句分析对话做关联
- ❌ 每条记忆加摘要/关键词元数据
- ❌ 后台定时任务 / 双模型异步合并
