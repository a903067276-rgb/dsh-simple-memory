# Review 监督插件 · 想法记录（2026-08-18）

> 状态：**想法已记录，未立项**。排在记忆系统落地之后（v2）。
> 归属：`dsh-simple-memory` 项目的衍生想法，独立小插件。

---

## 起因

聊 todo 执行机制时，用户问"有没有监督机制"。盘点后发现：DSH 自带沙箱/审批/退出码/git 留痕，但**没有"todo 标了完成 vs 产物实际存在"的自动核对**——todo 全绿只能证明 agent 声称做了。想补这道门禁，需要写一个小插件。

## 约束力分层（讨论结论）

| 层级 | 例子 | 约束力 |
|---|---|---|
| 系统硬机制 | 沙箱、审批弹窗、schema 校验 | 最强，绕不过 |
| 可执行脚本 | restart-dsh-web.sh（健康检查+重试） | 强，客观可验证 |
| 工具门禁 | 前置条件不满足不放行 | 中，看 DSH 是否提供 |
| 文字约定 | AGENTS.md 写"你要验证" | **弱，全凭自觉** |

**结论：AGENTS.md 是文字建议不是锁。文字管提醒，脚本管必须，插件管门禁。**

## Review 插件能管什么、管不了什么

**能核对（客观）**：
- todo 勾选时要求附产物证据：文件存在 / 内容含指定关键词 / 命令有退出码 / git 有 diff
- 会话收尾自动跑检查清单，逐项打勾
- 无证据则标记"未验证"提醒用户

**管不了（主观）**：
- 设计好不好、总结准不准、方向对不对——只能靠人（或模型）判断
- 插件核对的规则本身也是人写的，规则可以写松——它是"更强一点的约定"，不是绝对真理

## 绕不开的悖论

**谁 review review 插件？** 它验证"文件改了"，验证不了"改对了"。最终兜底仍是用户一句话抽查。价值定位：**挡住低级失误（忘了写、写了没存、路径错），不替代人把关。**

## 安排与复用

- 顺序：记忆系统本体（零代码）落地 → 再做 review 插件（v2）
- 技术路线：按老规矩，先动态 Cordis 插件热插拔验证"todo 勾选时核对产物"链路能否钩上（需查 DSH 是否有工具调用/事件钩子），再落静态 bundle
- 一鱼两吃：顺手把"记忆收尾提醒"做成硬机制（收尾必须过一遍"有没有值得记的"）
