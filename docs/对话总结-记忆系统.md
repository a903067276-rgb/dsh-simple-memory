# 对话总结：DSH 记忆系统（2026-08-18）

## 一、起因

用户问"DSH 的记忆有人做吗"，由此展开调研与讨论，最后决定自己做一个**简单版**记忆插件（`dsh-simple-memory`）。

## 二、调研结论（2026-08-18 实查）

- **官方没做**：deepseek-ai/deepseek-harness（13.8 万 star）内置包里**没有记忆模块**；官方讨论区「求一个 memory 能力」34 条评论，**官方零回复**。官方对记忆的态度是：不给记忆，给管道（会话存盘 + AGENTS.md 注入），策略自己写。
- **社区卷成一锅粥**：至少 10 个方案（bridge 派 / 原生派 / 重引擎派 / 极简派），但**全是 2026-08-14~16 刚出生的**，star 最高 12，无长期使用反馈；有人实测发现插件装完就报错（inject 声明缺失），作者修了两轮才发对。
- **核心痛点**（社区争论）：自动沉淀的 800 条 vs 手动写的 17 条——"自信的错记忆比没有记忆更危险"。
- **第三方情报**：dshbase.com/plugins/directory/ 有社区实测标注（dsh 用户维护）。

## 三、核心认知（对话中形成的观点）

1. **"记忆"是两件事**：记（存储）+ 忆（检索）。缺的不是记，是忆。
2. **AI 不会回忆，只会检索**：记忆价值 = 关键时刻捞到它的概率 × 相关性。
3. **好的记忆系统必须会"忘"**：全部塞进上下文 = 噪声淹没。CC 只加载前 200 行 / 25KB，Codex 30 天未用自动修剪。
4. **模型架构决定一切**：我的"记忆"= 被塞进上下文的东西；会话结束窗口清零，只剩硬盘；窗口约百万 token（约一本《三体》），但实际要留大头给对话本身。
5. **CC / Codex 都是"两层模型"**：
   - 第一层（你写的）：CLAUDE.md / AGENTS.md —— 手动规则，层级加载（全局 → 项目）
   - 第二层（AI 自动的）：Auto memory / Memories —— AI 自己写 md 笔记，下次自动读
   - **DSH 已有第一层（AGENTS.md ✅），缺的只是第二层**。
6. **简单办法成立**：md 文件 + 自动加载，不建数据库、不搞向量检索。Codex 的 Memories 机制（后台异步合并、双模型、限流）是"重"的参考，我们做"轻"的。

## 四、确定的架构（两层一升）

```
┌─ 积累层（半自动）─────────────────────┐
│  agent 提议 → 用户确认 → 写入           │
│  按项目分目录 md（超 200 行拆分）        │
└──────────────┬───────────────────────┘
               │ 升级（用户确认 + 抽象化）
┌──────────────▼───────────────────────┐
│  规则层（自动加载）                     │
│  L0 全局 AGENTS.md   ← 每次会话都带    │
│  L1 项目 AGENTS.md   ← 进项目才带      │
│  搜索：跨全部记忆，无边界               │
└──────────────────────────────────────┘
```

**设计原则**：
1. 升级必须人确认（防自动记错污染全局）
2. 默认只加载记忆精华（前 100~200 行），大头留硬盘按需取
3. 一切复用已有机制，不新增基础设施
4. 记忆目录：`~/Documents/DSH/memory/<项目>/YYYY-MM-DD.md`

**用户已确认的决策**：
- 提醒形式：**网页界面加记忆面板**（到点提醒 + 随时看/搜/补记）
- 记忆目录：`~/Documents/DSH/memory/`
- 插件名：`dsh-simple-memory`（用户自定，"simple"无拼写错误）

**待定事项**：
- 升级触发方式：用户还没明确回答"AI 自动升你事后查" vs "你点头才升"（架构文档暂写"必须人确认"）
- 提醒的具体时间点（每日定时 vs 会话收尾时）
